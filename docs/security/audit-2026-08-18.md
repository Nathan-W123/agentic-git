# Cybersecurity audit — 2026-08-18

Revision audited: `677127fbdadd8581c9ee9f7e8583b879bb701495`.

This is a static review of the control plane and its supporting services. No
code was changed, no service was run, and no dependency was installed. Line
references are to the revision above.

## Scope

- Authentication, session and API-token handling (`services/api-gateway/src/auth.ts`).
- Authorization and the role/permission model (`services/api-gateway/src/authorization.ts`).
- The HTTP request pipeline: origin policy, CORS, CSRF, rate limiting, security

  `services/workspace-manager/src/egress-gateway.ts`).

### 1. Default configuration lets any stranger who can reach the control plane run code on it (High)

Three defaults compose into remote code execution by an unauthenticated
attacker:

- Registration is open. `POST /api/v1/auth/register` is in the public route set
  and only closes when `COORD_DISABLE_REGISTRATION=1` is set
  (`services/api-gateway/src/server.ts:3430-3437`, `:3270-3277`). A new account
  becomes owner of its own organization, which carries `run_task`
  (`services/api-gateway/src/auth.ts:register`,
  `services/api-gateway/src/authorization.ts:20-49`).
- The Docker execution boundary is opt-in. `sandboxOptions()` returns
  `undefined` unless a project configures `sandbox`
  (`apps/cli/src/project.ts:768-778`), and task execution then runs the agent
  CLI directly on the host as the control-plane process user.
- The credential policy defaults to `host-login`
  (`apps/web/src/index.ts:179-182`), so a task submitted by that stranger falls
  back to the host owner's ambient vendor session
  (`apps/web/src/providers.ts:1975-1998`).

The result on a deployment that only set `POSTGRES_PASSWORD` and
`COORD_BOOTSTRAP_TOKEN` — which is exactly what `docker-compose.yml` and
`.env.example` ask for — is: register, create a repository, submit a task, and
the agent executes with the control plane's own privileges while spending the
host owner's vendor credit. The sandboxed terminal route is *not* part of this;
it correctly refuses when no sandbox is configured
(`apps/web/src/overlay.ts:863-870`). Ordinary task execution has no such
refusal.

Recommendations, in order of value:

1. Refuse to serve open registration unless the operator opts in explicitly
   (invert the flag: `COORD_ALLOW_REGISTRATION=1`), or refuse it whenever
   `COORD_BOOTSTRAP_TOKEN` is unset — the same "is this reachable by strangers"
   question the bootstrap token already asks.
2. Make `refuse` the default credential policy and require `host-login` to be
   chosen, so a task never silently spends a credential its submitter does not
   own.
3. Refuse to run a task submitted by a non-owner when no sandbox is configured,
   or at minimum log a startup warning naming the combination.

### 2. Child processes inherit the whole control-plane environment (High)

`sanitizeChildEnv` deletes exactly one variable:

```
const DENIED_CHILD_ENV = ["NODE_TEST_CONTEXT"];
```
`services/repository-service/src/process-runner.ts:69`, used at `:161-169` and
`:193`.

Every locally spawned agent CLI, preview process, and repository command is
started from `sanitizeChildEnv(process.env)`
(`apps/web/src/providers.ts:1343`, `:2548`, `:2854`, `:3718`;
`apps/web/src/preview.ts:463`, `:772`, `:942`). Those children therefore read:

- `COORD_CREDENTIAL_KEY` — the AES-256-GCM key for every user's stored vendor
  and GitHub credential (`services/workspace-manager/src/user-credentials.ts:243-257`),
- `COORD_DATABASE_URL` — full Postgres credentials for the coordination store,
- `COORD_BOOTSTRAP_TOKEN`, and any provider API keys present on the host.

So any code that reaches a subprocess — a prompt-injected agent, a repository's
own test command, a preview server started from an imported repo — can decrypt
every user's credentials and connect to the database directly. This is the
mechanism that turns finding 1 from "code execution as the service user" into
"full compromise of every account's third-party credentials", and it is also
reachable by an ordinary trusted developer who was never granted those secrets.

Recommendation: replace the deny-list with an allow-list — build the child
environment from `PATH`, `HOME`, locale, proxy variables and the per-task
additions the caller passes, rather than from `process.env`. As a cheaper first
step, strip `COORD_*` (and any `*_TOKEN`/`*_KEY`/`*_PASSWORD`) from
`DENIED_CHILD_ENV`, and read `COORD_CREDENTIAL_KEY` into memory at boot then
`delete process.env["COORD_CREDENTIAL_KEY"]`.

### 3. Rate limiting keys on the TCP peer address (Medium)

The limiter key is `${ip}:${authRoute ? "auth" : "api"}` where `ip` is
`request.socket.remoteAddress` (`services/api-gateway/src/server.ts:3219-3229`,
`:15107-15109`). Nothing reads `X-Forwarded-For`, and there is no trusted-proxy
setting.

The documented deployments (`railway.json`, the compose control plane behind a
platform router) all put a proxy in front, so every request arrives from one
address and shares one bucket. Two consequences:

- Denial of service: the auth limiter is 10 requests/minute
  (`services/api-gateway/src/server.ts` constructor, `authRateLimitPerMinute`
  default). One client can exhaust it for the whole deployment, locking
  everybody out of sign-in.
- Password guessing is throttled globally rather than per account, and there is
  no per-account failed-login counter or lockout anywhere in
  `AuthService.login`.

Recommendation: add an explicit trusted-proxy hop count and derive the client
address from `X-Forwarded-For` when set (never trusting it unconditionally),
and add a per-account failed-login counter with backoff.

### 4. The Docker sandbox runs as root by default (Medium)

`resolveOptions` leaves `user` undefined unless configured
(`services/workspace-manager/src/docker-workspace-manager.ts:262-266`), and
`--user` is only emitted when set (`:422`). `apps/cli/src/project.ts:768-778`
passes it through only when the project config names one, so the shipped
default is UID 0 inside the container, with the task worktree bind-mounted
read-write (`:424-430`).

The rest of the sandbox is well built and should be said so: `--network none`
by default, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--read-only`
root filesystem, tmpfs `/tmp`, pids/memory/cpu limits, `.git` masked read-only,
and Docker tokens validated against injection before they reach the command
line. Running as root undercuts that: files the agent creates land root-owned
on the host worktree, and any container-escape primitive starts from UID 0.

Recommendation: default `user` to a non-root UID/GID (matching the host user
that owns the worktree), keeping the config override for images that need
otherwise.

### 5. `.env` is not git-ignored (Medium)

`.gitignore` covers `node_modules/`, `dist/`, `.turbo/`, `.coordinator/`,
`coverage/`, `*.tsbuildinfo` and `.model-cache/` — not `.env`. Meanwhile
`docker-compose.yml:6-10` instructs operators to keep `POSTGRES_PASSWORD` and
`COORD_BOOTSTRAP_TOKEN` "in a `.env` file next to this compose file", and this
repository is one an operator is expected to clone and then push from (the
export-to-GitHub path is a first-class feature).

Recommendation: add `.env` and `*.env` (with `!.env.example`) to `.gitignore`.
While there, add `COORD_CREDENTIAL_KEY` to `.env.example`: compose already
forwards it, but nothing tells an operator it exists, which is why finding 9's
fallback is the common case.

### 6. Attachment type is taken from the uploader's claim (Low)

`AttachmentStore.save` picks the stored extension from the request's declared
`Content-Type` and never inspects the bytes
(`apps/web/src/attachments.ts:51-70`). A caller with `run_task` can therefore
store arbitrary bytes as `…​.png`.

Impact is contained rather than absent: the read path derives the response type
from the allow-listed extension, sends `X-Content-Type-Options: nosniff`, and
SVG is deliberately excluded (`apps/web/src/attachments.ts:14-24`,
`services/api-gateway/src/server.ts:5820-5830`), so a browser will not execute
what it is handed. The residual risk is hosting attacker-chosen bytes on a
trusted origin.

Recommendation: check magic bytes against the claimed type before writing.

### 7. Secure cookies off by default, no HSTS (Low)

`secureCookies` defaults to `false` (`apps/web/src/index.ts:638`,
`services/api-gateway/src/auth.ts` constructor) and `docker-compose.yml` passes
`${COORD_SECURE_COOKIES:-false}`, so a TLS deployment whose operator missed the
variable issues session cookies without `Secure`. `securityHeaders`
(`services/api-gateway/src/server.ts:15112-15127`) sends nosniff, `DENY`,
`no-referrer`, a Permissions-Policy and a CSP, but no
`Strict-Transport-Security`.

`HttpOnly` plus `SameSite=Strict` limits the exposure to an active network
attacker on a plaintext hop. Recommendation: default `secureCookies` to true
when the request arrives over TLS (or `X-Forwarded-Proto: https`), and emit HSTS
on those deployments.

### 8. `style-src 'unsafe-inline'` (Info)

The CSP keeps `script-src 'self'`, `object-src 'none'`, `base-uri 'none'` and
`frame-ancestors 'none'`, and relaxes only styles for Monaco's runtime theming
(`services/api-gateway/src/server.ts:15118-15127`). That is a reasonable trade
and is documented in place. It leaves CSS-based exfiltration available to any
future HTML-injection bug; worth revisiting if Monaco is ever swapped or
nonce-able.

### 9. Credential key fallback (Info)

With `COORD_CREDENTIAL_KEY` unset, a key is generated and written mode `0600`
next to the encrypted credential file
(`services/workspace-manager/src/user-credentials.ts:258-277`). The code says
plainly what that protects — copied backups and stray reads, not an attacker who
owns the project directory. Correct as written; see finding 5 for the
documentation gap that makes this the default in practice.

### 10. Audit chain is detection, not prevention (Info)

`services/persistence/src/audit-chain.ts:1-55` folds each event's payload hash
into a chain hash, with canonical JSON so key order cannot change a digest.
Anyone with write access to the store can recompute the chain — as the module
documents. Off-box shipping or periodic external anchoring of the head hash
would close that, if the threat model calls for it.

## Checked and found sound

Recorded so a later reviewer does not repeat the work:

- **Password handling.** scrypt (N=16384, r=8, p=1, 64-byte output, per-user
  salt), a constant dummy digest so login timing does not reveal account
  existence, `timingSafeEqual` throughout, and a composition policy
  (`services/api-gateway/src/auth.ts:205-256`, `:410-436`). N is a little below
  current OWASP guidance (2^17) but is a defensible cost choice.
- **Credential storage.** Sessions, API tokens and invitations are stored only
  as SHA-256 digests of high-entropy random secrets and compared in constant
  time; the plaintext of an API token exists once, at issue
  (`services/api-gateway/src/auth.ts:104-127`, `:490-560`). Vendor credentials
  are AES-256-GCM with a random IV per record and an authentication tag
  (`services/workspace-manager/src/user-credentials.ts:360-395`).
- **CSRF and origin policy.** Cookie sessions require a double-submit token that
  is *also* checked against the session's stored hash; bearer tokens skip it
  with a correct justification; `SameSite=Strict`, `HttpOnly`; state-changing
  methods only (`services/api-gateway/src/auth.ts:770-800`,
  `services/api-gateway/src/server.ts:3288-3304`). Origin is validated against a
  parsed, credential-free allow-list, and CORS echoes only allow-listed origins
  (`:2996-3010`, `:15075-15104`).
- **Authorization.** A single role→permission table with rank ordering, resolved
  per request from live memberships; tokens can only narrow a role, never widen
  it; every repository route runs through `authorizeRepository`
  (`services/api-gateway/src/authorization.ts`, 73 call sites in `server.ts`).
  Overlay routes bind the scope to the authenticated principal's own user id and
  require `run_task` for exec versus `submit_task` for edits
  (`services/api-gateway/src/server.ts:6125-6145`).
- **Command execution.** `spawn` with `shell: false` everywhere, explicit PATH
  resolution, output and timeout bounds, tree kill on Windows, and Windows batch
  tokens rejected rather than quoted
  (`services/repository-service/src/process-runner.ts:120-260`).
- **Git credentials.** Passed as `GIT_CONFIG_KEY_0=http.extraHeader` in the
  child environment rather than in argv or a URL, with CR/LF/NUL rejected and
  `GIT_TERMINAL_PROMPT=0` (`services/repository-service/src/repository-service.ts:1752-1787`).
  Remote URLs are normalized and refused if they carry credentials, a query, a
  fragment, or a non-HTTPS/SSH scheme (`:1677-1748`).
- **SQL.** Both stores use bound parameters; the only interpolated identifiers
  are from fixed literal arrays in the source
  (`services/persistence/src/postgres-store.ts:1590-1606`, `:2600-2615`;
  same shape in `sqlite-store.ts`). No user-controlled identifier reaches SQL.
- **Browser rendering.** One escaping helper covering `& < > " '`
  (`apps/web/public/ui.js:18-29`), applied *before* markup is generated;
  `richText` escapes first and then constructs a deliberately tiny subset —
  bold, code, headings, lists, mentions, slash commands — with no links, images
  or raw HTML (`apps/web/public/screen-chats.js:575-640`). Mention names are
  regex-escaped before being compiled into a pattern.
- **Static assets.** Both the dashboard and the vendored Monaco tree are served
  from allow-lists rather than by path resolution
  (`apps/web/src/assets.ts:13-47`); attachment ids are matched against
  `^[0-9a-f]{32}\.(png|jpg|gif|webp)$` before touching the filesystem.
- **WebSockets.** Origin asserted and the session authenticated at upgrade, then
  re-authorized periodically against live membership and revocation
  (`services/api-gateway/src/server.ts:3024-3060`); frames must be masked, and
  message, buffer and fragment sizes are bounded
  (`services/api-gateway/src/ws-frame.ts:108-260`).
- **Egress.** When configured, the agent joins an `--internal` network with a
  CONNECT-only proxy as the sole route out, allow-list entries validated as
  hostnames, and a bare `.` refused
  (`services/workspace-manager/src/egress-gateway.ts:11-95`).
- **Invitations.** The link's secret is hashed at rest, every failure mode
  answers 404 identically, and an invitation for an address that already has an
  account requires signing in as that account
  (`services/api-gateway/src/server.ts:3498-3600`).
- **Supply chain.** The runtime dependency surface is three third-party packages
  (`pg`, `wink-lemmatizer`, `wordnet-db`) plus the vendored editor; everything
  else is workspace-internal. No committed private keys or provider tokens were
  found (the GitHub device-flow client id in the Dockerfile is a public
  identifier, correctly noted as such).

## Suggested order of work

1. Environment isolation for child processes (finding 2) — smallest change, and
   it is what bounds the blast radius of everything else.
2. Registration/credential-policy/sandbox defaults (finding 1).
3. `.env` in `.gitignore` and `COORD_CREDENTIAL_KEY` in `.env.example`
   (finding 5) — one-line changes.
4. Proxy-aware rate-limit keying and per-account login backoff (finding 3).
5. Non-root sandbox user (finding 4).
6. Attachment magic-byte check, Secure-cookie/HSTS defaults (findings 6, 7).

## Do the fixes change how the app works?

Asked after the audit: would applying these recommendations change the
underlying function of the application? Assessed against the same revision, on
the same reading — no code was run.

The short answer is that none of them change what the app *does*. Nothing here
removes a feature, changes a screen, alters the task lifecycle, or changes any
stored shape. Four of them change a **default**, and a default that currently
permits something is exactly what most of these findings are — so a deployment
relying on that permission would notice. Those four are 1, 3, 4 and 7. The rest
are invisible in normal use.

| # | Changes behaviour? | What somebody would notice |
|---|--------------------|----------------------------|
| 1 | Yes — three defaults | Strangers can no longer self-register; tasks stop falling back to the host owner's vendor session |
| 2 | No, with a caveat | Nothing, unless a spawned command silently depended on an inherited variable |
| 3 | Yes, mostly in the good direction | Limits count per client instead of per deployment; repeated wrong passwords now lock one account |
| 4 | Yes, for sandboxed deployments | Files the agent creates stop being root-owned; an image needing root fails until it is told otherwise |
| 5 | No | Nothing at runtime |
| 6 | No, for genuine images | A mislabelled upload is rejected at upload time instead of stored |
| 7 | Yes, for plaintext deployments | Sign-in breaks over plain HTTP unless the default is conditioned on TLS |
| 8 | No | Nothing — no change recommended |
| 9 | No | Nothing — documentation only |
| 10 | No | Nothing in the app; adds an external destination if adopted |

### The four that need an operator decision

**1 — registration and credential policy.** Closing registration by default is
felt only by deployments that intend to be publicly joinable; existing accounts,
sign-in and invitations are untouched, and the invitation path already covers
the legitimate case of adding people. The riskier half is making `refuse` the
default credential policy (`apps/web/src/index.ts:179-182`). On a deployment
where nobody has connected their own provider account — the single-operator case
this project started from — every task today runs on the host's ambient vendor
session, and flipping that default stops those tasks until each user connects a
credential or the operator sets `COORD_CREDENTIAL_POLICY=host-login` back. That
is the one recommendation in the report with a real chance of stopping a working
install, and it should ship with the variable named in `.env.example` and in the
deployment docs rather than silently.

**3 — rate-limit keying and login backoff.** Reading the client address through
a configured proxy hop makes the limiter behave the way it was always meant to:
one noisy client stops consuming everybody's budget. The new behaviour is the
per-account backoff, which introduces a failure a legitimate user can hit — get
your own password wrong enough times and you wait. The hazard is
misconfiguration rather than the fix: a deployment with no proxy that trusts
`X-Forwarded-For` lets any client choose its own bucket, which is why the hop
count has to be explicit and default to zero.

**4 — non-root container user.** For unsandboxed deployments this changes
nothing, because `--user` is only emitted when a sandbox is configured
(`services/workspace-manager/src/docker-workspace-manager.ts:424`). For
sandboxed ones the visible change is the point of the fix: files the agent
writes into the bind-mounted worktree stop landing root-owned on the host. The
regression risk is an image whose entrypoint installs packages or writes outside
`/tmp` and the worktree; those fail as non-root, and the existing `sandbox.user`
config key is the escape hatch.

**7 — Secure cookies and HSTS.** Setting `secureCookies` unconditionally would
break every plain-HTTP deployment — a LAN box, a localhost host name — because
the browser then refuses to send the session cookie at all and sign-in appears
to silently fail. Conditioning it on the request actually arriving over TLS (or
`X-Forwarded-Proto: https`), as the finding recommends, keeps those deployments
working. HSTS deserves its own note: it is the one change here a user cannot
undo from the app, because the browser remembers it for the domain.

### The ones with no user-visible effect

**2 — child environment.** This is the largest change by code volume and the
smallest by behaviour. Credentials already reach a vendor CLI through an
explicit per-run environment: `openCredentialHome` copies the base environment,
strips every credential variable, and adds the caller's own
(`services/workspace-manager/src/user-credentials.ts:1124-1140`, `:999-1007`),
and host-login works from a home directory rather than an inherited secret. So
an allow-list carrying `PATH`, `HOME`, locale, proxy variables and the caller's
additions preserves every path the app itself uses.

Two caveats worth planning for. First, the allow-list should be assembled from
what real runs read, not guessed: a repository's own test or preview command may
expect a variable nobody here listed, and that failure would surface as a broken
build rather than as a security change. Second, the cheap first step — reading
`COORD_CREDENTIAL_KEY` at boot and deleting it from `process.env` — is only safe
while every credential store is opened before the delete. The key is resolved
once per store and then held in memory
(`services/workspace-manager/src/user-credentials.ts:319-331`), and the entry
point does open one store eagerly and inject it
(`apps/web/src/index.ts:154-161`), but `ProviderChatService` will lazily open its
own when none is injected (`apps/web/src/providers.ts:1606-1611`). A lazy open
after the delete would find no key, fall back to the generated key file, and
fail to decrypt credentials that were written under the configured one — a data
outcome, not an error message. Thread the key in rather than relying on ordering.

**5, 8, 9, 10.** Ignoring `.env` and documenting `COORD_CREDENTIAL_KEY` change
nothing a running deployment reads; an already-committed `.env` stays committed
and still needs its secrets rotated. Findings 8, 9 and 10 recommend no code
change at all — 8 accepts the trade, 9 records that the fallback is correct as
written, and 10 notes that external anchoring is an operational addition, not an
application one.

**6 — attachment magic bytes.** Every genuine PNG, JPEG, GIF or WebP passes
unchanged; the read path is not touched. The only new refusal is an upload whose
bytes do not match its declared type, which is the intent — though a file with
an unusual but valid variant header would also be refused, so the check should
be permissive about container details and strict only about the leading
signature.

### Summary

Safe to apply without an operator conversation: 2 (in its cheap form), 5, 6, and
the proxy-aware keying half of 3. Needing a decision, a documented variable and a
release note: 1, 4, 7, the login backoff, and the full allow-list of 2. Nothing
in the list removes or disables a feature of the app.
