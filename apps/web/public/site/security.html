Security.

What is isolated from what, and what has to happen before a change lands.

One copy of the repository

The canonical repository lives with the deployment that runs it, which while KUMI is hosted means our servers rather than yours. There is one copy, not one per agent, and nothing is automatically pushed anywhere else. A self-hosted deployment, where that machine would be yours, is not open yet.

Agents do not touch it

Every agent and every person editing through the dashboard works in a detached git worktree owned by exactly one principal. Ownership is checked on every access against the authenticated caller, and a workspace identifier is never accepted from the client.

Execution is sandboxed

Agent commands run inside an optional Docker boundary that is deny-by-default on the network, can write only inside its own workspace, has a read-only root, and has the repository's Git metadata masked from it.

Changes are gated

A plan is validated before a workspace is granted. Files are leased, so overlapping work is scheduled rather than merged afterwards. Validation commands run in a temporary snapshot, and promotion into the canonical repository is one atomic compare-and-swap at a time. Plan, scope and changeset approvals are available as gates.

Everything is recorded

The audit timeline is append-only and hash-chained, scoped by tenant, project and run, and verifiable across both archived and live events. Access is role-based: owner, admin, developer, reviewer and viewer.

Nothing leaves without you

Repositories are imported over HTTPS or SSH with credentials kept out of the stored configuration. The only path back to GitHub is an explicit one-way export onto a dedicated branch, which refuses to run if the upstream has moved since import.

Reporting a problem

KUMI is pre-launch and has not been through an external security audit. If you find something, we would rather hear it early: say so on the waitlist form and we will come back to you.
