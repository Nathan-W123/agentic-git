Questions.

What KUMI is, what it does with your code, and what it does not do yet.

What is KUMI?

A coordination layer between the people on a team, the coding agents working with them, and one shared codebase. It is not another coding agent: it runs the ones you already use, decides who touches what, and carries context between them.

Which agents does it run?

Claude, Codex and Cursor are the ones we have verified end to end, and they are the three named on the front page for that reason. Adapters are written for Gemini, Copilot and Kiro, and there is a generic JSONL protocol for anything else that can speak it, but we are not claiming those until they have been run properly. You sign in with the accounts and subscriptions you already pay for.

Where does my code live?

On our servers, while KUMI is hosted. The repository sits with the deployment that runs it, and today that deployment is ours rather than yours. There is one copy of it, not one per agent, and no agent edits it directly: each works in an isolated git worktree of its own. Underneath it is ordinary Git, so every change that lands is a real commit in a real repository.

Does it push to my GitHub?

Only when you ask. Import is a clone. The one path back out is an explicit, one-way export onto a branch of its own, and it refuses if the upstream has moved since the import.

What happens before a change lands?

An agent files a plan, which is validated before it is allowed a workspace. Files are leased, so two agents cannot quietly edit the same one. Changes are validated, reviewed at the gates you configure, and promoted one at a time.

What if two agents want the same file?

The coordinator settles it rather than letting both proceed and merging afterwards. One gets the file, the other is told, and a plan that has gone stale is replanned against the new head.

Is it open yet?

Not yet. The waitlist is how you hear when it is.

Can I run it myself?

Not yet, and it is the thing we most want to offer. KUMI is built as one control plane with workers that can execute on other machines, which is the shape a self-hosted or on-premises deployment needs. Today it only runs on ours.
